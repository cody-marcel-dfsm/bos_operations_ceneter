# Calimatic recovery opened a second BOS login

## User-visible evidence

On 2026-09-03, a user who had already authenticated the root BOS MCP connection
and completed Gmail provider authorization requested Calimatic authentication.
The returned browser page displayed **Sign in to authorize BOS** instead of the
Calimatic portal URL and API-key form. After the user confirmed that BOS was
already authenticated, the client itself reported that the Calimatic recovery
page was incorrectly gated on a separate BOS web session.

User-supplied screenshot SHA-256 values:

- Full recovery trace and BOS sign-in browser surface:
  `90cd92d50d170a0ed3f872bf9d378aedf3b50dbf7bb375f3fda6495ff74f96bd`
- Client confirmation that BOS MCP remained authenticated while the provider
  transaction stayed pending:
  `04f288296c83fc746e509613917d25562a3863ee1a2433e193a717c4dbdd707a`

## Sanitized runtime chronology

The matching local task trace establishes this order without retaining any
credential, context identifier, recovery token, or query string:

1. `bos_get_context` succeeded through the authenticated root BOS MCP resource.
2. `bos_list_plugin_services` succeeded for the selected organization and
   returned the Calimatic service state.
3. `bos_begin_plugin_service_connection` returned
   `authorization_required` with `authorization_kind: api_key` and a short-lived
   `/api/v1/mcp/provider-recovery` URL.
4. The client opened that exact server-returned URL. Its first surface said
   **Sign in to authorize BOS**, linked to the BOS application, and waited for a
   BOS web session instead of showing the Calimatic credential collector.
5. The client followed the BOS link and initiated root Google/BOS consent even
   though the authenticated MCP calls had already proved the BOS grant.
6. The page later said it was continuing, while the provider transaction
   remained pending and never presented the Calimatic form. A later recovery
   attempt expired.

## Root cause

The server-issued API-key provider recovery transaction depended on a distinct
BOS browser cookie. That introduced a second BOS identity boundary after the
MCP bearer-authenticated request had already established the actor and scoped
transaction. The client compounded the server defect by treating the recovery
page's BOS sign-in link as authoritative and following it.

The root BOS grant, Gmail provider grant, and Calimatic API-key credential are
three separate states. The existing BOS grant authorizes creation of a
transaction-bound Calimatic credential collector. It does not require a second
BOS login. Gmail readiness neither supplies nor invalidates Calimatic readiness.

## Required correction

- The server binds the short-lived recovery URL to the already authenticated,
  installation-scoped provider transaction and serves the Calimatic portal URL
  and API-key collector directly.
- The recovery page never redirects to, links to, or waits for root BOS sign-in.
- The client validates that an API-key recovery URL presents the provider
  credential collector. A root BOS sign-in surface produces
  `provider_recovery_identity_boundary`; the client preserves and polls the
  original transaction once and never launches BOS authentication.
- Successful submission completes the same provider transaction, after which
  the client verifies status and resumes the original operation once.

This repository owns and implements the client guard. The BOS server repository
owns the transaction binding, recovery page, persistence, and deployment.
