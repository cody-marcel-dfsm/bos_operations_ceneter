# 0.4.80 static-catalog copy correction

## Observed evidence

The BOS plugin detail page described installed subservice plugins as adding
domain workflows through “a complete static operation catalog.” The user
corrected that statement: BOS is not a static registry; it provides dynamic,
domain-specific MCP services and tooling.

User-supplied screenshot SHA-256:
`4add97a85255b6d32398b4269d386b8c13777ab94a5e55250bd21c7933db60d2`.

The screenshot shows the rendered 0.4.80 marketplace long description. Its
incorrect sentence came directly from `products/bos/product.json` and therefore
propagated deterministically to the generated client manifests.

## Root cause

The 0.4.78–0.4.80 client contract collapsed two different concepts:

- the stable root BOS MCP transport and authentication boundary; and
- the services and tools that BOS resolves dynamically for a domain and current
  authenticated scope.

That conflation produced inaccurate marketplace copy and client instructions
that treated `tools/list` as an invariant registry across plugin, capability,
provider, role, installation, and service changes.

## Correct contract

- The root BOS package owns one stable authenticated MCP connection.
- BOS dynamically resolves domain-specific MCP services and their current
  tooling through that connection.
- Clients use live tool discovery and refresh it after connection, context,
  installation, role, plugin, capability, provider, license, domain-service, or
  schema changes that may alter the exposed surface.
- Tool presence declares a currently exposed operation and schema. The server
  still revalidates authority when `tools/call` executes.
- Historical records describing the complete static catalog remain preserved as
  superseded evidence and do not define the current architecture.
