# Codex 0.4.78 plugin authentication and session RCA

## Observed states

Two user-provided screenshots on 2026-09-02 and the matching server trace
establish these separate states in Codex Desktop 26.831.21537:

1. The installed BOS plugin detail page lists the `Platform` MCP server without
   a **Connect** action. The server trace proves the BOS grant was valid at that
   time, so this screenshot is an authenticated or indeterminate UI observation;
   it does not prove that a signed-out authentication action is missing.
   Screenshot SHA-256:
   `a58760576881abe2814b8c0a2606e441e6ec2df1ea6de72b38ed38ee6d29e9f4`.
2. A fresh task presents a false signed-out state even though the existing BOS
   OAuth grant is preserved and reused.
3. The exact request `sign into gmail plugin on bos` falls back to prose telling
   the user to find a Login, Connect, or Authenticate control instead of using
   the BOS MCP server and presenting native authentication only if BOS requires
   it. Screenshot SHA-256:
   `ebf7702529b1dcd5d7e7dd15b65e693d2d3a05651dd95eb5f573361005f2a373`.

## Runtime evidence

The task log repeatedly records:

`mcp.runtime.resolve_for_step: omitting pending optional MCP server server_name=platform`

The same desktop account later loads the existing credential for the same
`platform` resource identity and initializes `bos-remote-agent-gateway`
successfully. This localizes the cross-task failure to package/runtime startup
classification. It does not indicate separate credentials per task or a
server-side session boundary.

The server-side trace supplied after the screenshots confirms the grant refresh
succeeded at 20:15 MDT, six authorized contexts remained valid, and no
revocation, replay, or `invalid_grant` occurred. Two authenticated `tools/list`
requests then took about 30.9 seconds, crossed the server's 30-second deadline,
and returned HTTP 200 JSON-RPC timeout results. At 20:19 the same client retried
without another token exchange and received all 49 authorized tools in 27.45
seconds. Screenshot SHA-256:
`108bd9527aa6f3949a18b5b700f398f6084807ca6ea6eb4083ccb49570760307`.

This establishes a server-side discovery-performance defect alongside the
client defects. The missing catalog was caused by authenticated discovery timing
out; the client then misclassified that missing catalog as a login requirement.
Initial unauthenticated GET 401 responses remain normal OAuth discovery probes.

`codex mcp list --json` confirms that the installed `platform` entry is OAuth
capable, while `codex mcp get platform --json` shows neither an explicit OAuth
resource nor required startup. The generated 0.4.78 `.mcp.json` contains only
`type` and `url`.

## Root cause and correction

The package declares the correct single BOS endpoint and the marketplace
correctly declares `authentication: "ON_INSTALL"`. The generated MCP server
entry omits host-supported identity and startup requirements needed by this
product contract:

- `oauth_resource` equal to the canonical BOS MCP resource URL, so every task
  and every BOS-owned skill resolves the same credential boundary;
- `required: true`, so the host waits for the root BOS server's authoritative
  state instead of silently dropping a pending optional server from a task;
- `startup_timeout_sec: 45`, so required startup can reach BOS's bounded result
  despite the observed 27.45-second successful discovery and 30-second server
  deadline instead of failing at Codex's documented 10-second default.

These fields do not decide whether a user needs to authenticate. BOS remains the
authority: the server either accepts the reusable credential or returns its OAuth
challenge. The client renders **Connect** only for the latter state and reuses the
authenticated BOS connection for the former.

The server owner is replacing per-tool discovery authorization with a bounded
two-stage contract. Authenticated `tools/list` validates the BOS token once,
confirms access to at least one organization, and returns the complete static
BOS operation/schema catalog without per-tool, provider-health,
plugin-credential, or role filtering. `tools/call` then validates the selected
opaque organization context and performs operation-specific capability and
provider authorization.

The client treats catalog entries as operation/schema declarations rather than
authority or provider-readiness evidence. It refreshes context or operation
status after permission, role, plugin-enablement, capability, or provider
changes, and starts provider recovery only from the selected call's structured
response. The package correction makes the root server mandatory, preserves its
OAuth identity, and gives discovery an adequate client budget. These fields do
not themselves prove or cause native plugin-detail authentication rendering.

The package generator, validators, installer checks, runtime inspection, and
regression tests now require all three fields. The package continues to contain one
generated `.mcp.json`, no `.app.json`, no independent connector registry record,
and no OpenAI or ChatGPT authorization target.

## Acceptance

Deterministic checks must prove the generated package contains one `platform`
entry with `url === oauth_resource ===` the product-owned BOS resource and
`required === true`, with a 45-second startup timeout. Final Issue #0001 closure still requires a signed-out,
version-matched plugin-detail screenshot showing native **Connect** and a second
task proving that an existing BOS login is reused without another login prompt.
The latter must also show successful authenticated tool discovery within the
effective deadline.
