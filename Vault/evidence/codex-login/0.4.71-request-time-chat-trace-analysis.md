## Causal reclassification

The deployed BOS endpoint's HTTP 401 response to a synthetic unauthenticated
MCP `initialize` probe is valid server-contract evidence. It is not causal
evidence for this customer prompt because the real prompt never selected a BOS
tool, loaded a BOS server, or contacted that endpoint.

Current official Codex source at commit
`ddf8a67ab09cd76b8adc0969f11ee1271179aba7` confirms the host activation gap:

- `codex-rs/core/src/session/turn.rs` collects `app://` IDs from skills only
  after those skills were explicitly mentioned and injected before sampling;
- `codex-rs/core/src/mcp_tool_call.rs` requests connector auth elicitation only
  after a `codex_apps` tool call returns `connector_auth_failure`; and
- endpoint plugin recommendations in `turn.rs` take precedence over legacy
  connector discovery, so an installed plugin's inaccessible app connector is
  not offered through the fallback install/connect tools in that mode.

Two exact-prompt app-server reproductions after linking a package-skill
experiment produced no `mcpServer/elicitation/request`. Thread
`01a0600b-d120-7d13-80c2-e9c3b8eb21f8` rendered the `app://` mention as manual
prose. Thread `01a0600e-066a-75d2-b722-7e46de1ab735` enabled tool suggestion,
but the model read the skill with local `exec` after sampling had already begun
and again returned manual sign-in instructions. The experiment was removed.

The install-suggestion experiment and its uncompiled candidate patch were
withdrawn after this live result. `request_plugin_install` owns plugin discovery
and installation; it does not own an installed connector's OAuth recovery.

The next causal review corrected an important false premise in the earlier
analysis. Official OpenAI plugin authentication guidance says the client starts
OAuth when the user first invokes a tool. Tool-level OAuth UI requires both a
descriptor with per-tool `securitySchemes` and an unauthenticated selected-tool
result with `_meta["mcp/www_authenticate"]`. Therefore Codex needs the requested
BOS tool's metadata before consent. This is capability metadata, not authorized
business access: customer data and business execution remain denied until the
token passes issuer, audience, expiry, and scope validation.

The request-time auth owner is the selected OAuth-declared BOS tool. Its
signed-out error result must carry `resource_metadata`, `error`, and
`error_description`, causing the host to render the native inline action. After
consent, Codex refreshes authority-scoped tool state, calls `bos_get_context`,
executes the requested read, and continues the same turn. Codex-owner and
BOS-server-owner implementation, focused tests, signed-client integration, and
the genuine Desktop acceptance flow remain required.

At `2026-09-01 21:47 America/Denver`, the new client-owned
`contract:oauth-tool-auth-live` probe ran against the deployed BOS platform
resource. The first unauthenticated `initialize` request returned HTTP 401 with
the protected-resource challenge. The probe therefore could not reach
`tools/list`, find the `bos_get_context` OAuth descriptor, or invoke that tool to
obtain `_meta["mcp/www_authenticate"]`. This is the exact selected-tool contract
failure. The challenge itself remains valid discovery evidence; it does not
present the tool-bound chat action.

The current causal sequence is:

1. The BOS skill and required app declaration load.
2. The exact prompt identifies the Plugin Console capability, but no matching
   OAuth-declared BOS tool descriptor is available for selection.
3. With no selected BOS tool invocation, no
   `_meta["mcp/www_authenticate"]` result can reach the host.
4. The only model-callable connector suggestion path owns plugin installation;
   accepting it opens an external ChatGPT plugin page.
5. The inline BOS login action never renders, so the preserved request cannot
   continue through consent and the requested read.

Keep BOS business execution protected. Expose only the requested tool's
descriptor and OAuth scopes before consent. A matching customer request selects
that tool; its signed-out invocation returns the canonical
`mcp/www_authenticate` challenge without executing business logic. The host
renders the tool-bound native action, completes OAuth, refreshes
authority-scoped tool state, and resumes the same turn. Endpoint plugin
recommendations, declaration-only preflight, and anonymous bootstrap business
tools must not suppress or replace this selected-tool flow.
